# Security

> **Status: SHIPPED.** RLS via `#[model(tenant_key = "...")]` plus the
> `DjogiAuth` trait, `AuthContext`, password hashing, and per-tenant
> auto-`set_tenant` shipped through Phases 5 + 5.5. The authoritative
> current API lives in [`docs/guide/auth.md`](../guide/auth.md) and
> [`docs/guide/tenancy.md`](../guide/tenancy.md). This roadmap document
> is preserved as design history — the snippets here may not match the
> shipped surface byte-for-byte.

This guide covers Row Level Security (RLS) isolation for multi-tenant models, the `_insecurely()` escape hatch, the `DjogiAuth` trait, role switching, schema snapshot signing, and common security anti-patterns.

Security in Djogi is enforcement by default. Tenant-scoped models require explicit tenant context to query. Bypassing isolation requires deliberate action and leaves an audit trail.

---

## 1. Row Level Security Overview

PostgreSQL Row Level Security restricts which rows a connection can see and modify based on session-level variables. Djogi integrates RLS at the framework level for models annotated with `#[model(tenant_key = "...")]`.

**When to use RLS:**

- Your application serves multiple tenants (organizations, workspaces, accounts) and the data for different tenants must be isolated at the database level.
- You want isolation that holds even if application code has a bug — a query that forgets a `WHERE org_id = $1` clause should return zero rows, not all tenants' data.
- You need a compliance guarantee that cross-tenant data leaks are structurally impossible, not just policy-enforced.

**When not to use RLS:**

- Single-tenant applications where all data belongs to one owner.
- Reference data tables (country codes, fuel types) that are intentionally shared across all tenants.
- Tables that RLS would complicate with no security benefit (internal infrastructure tables).

RLS adds a Postgres policy check to every query on the table. The performance cost is a single config variable read per query — negligible in practice. The safety benefit is that even a SQL injection attack against your query layer cannot cross tenant boundaries.

## 2. `#[model(tenant_key = "field")]`

Annotating a model with `tenant_key` tells Djogi to:

1. Add a `UNIQUE`-indexed column for the tenant key (you provide it as a regular field)
2. Generate RLS policy SQL during `cargo djogi migrate`
3. Require tenant context on all queries and writes via `QuerySet`
4. Add `_insecurely()` variants to every terminal method for admin use

```rust
use djogi::prelude::*;

#[derive(Model, Debug, Clone, Serialize, Deserialize)]
#[model(table = "invoices", tenant_key = "org_id")]
pub struct Invoice {
    pub org_id: HeerId,          // tenant discriminator — explicit field, not injected
    pub number: String,
    pub total_cents: i64,
    pub status: String,
    pub due_date: time::Date,
}
```

Running `cargo djogi rls` shows the generated policy SQL before it is applied:

```sql
-- Generated by: cargo djogi rls

ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE ROW LEVEL SECURITY;

CREATE POLICY invoices_tenant_isolation ON invoices
    USING (org_id = current_setting('djogi.tenant_id', true)::bigint)
    WITH CHECK (org_id = current_setting('djogi.tenant_id', true)::bigint);

-- App role sees only tenant rows; admin role bypasses policy
GRANT SELECT, INSERT, UPDATE, DELETE ON invoices TO djogi_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON invoices TO djogi_admin;

ALTER POLICY invoices_tenant_isolation ON invoices
    TO djogi_app;  -- policy applies to djogi_app role only
```

`cargo djogi migrate` applies this SQL automatically when it detects a model with `tenant_key`.

## 3. `djogi::set_tenant(tx, tenant_id)`

For RLS to work, every database transaction that accesses tenant-scoped tables must set the tenant context before any query fires. Djogi does not set this automatically — you set it explicitly in your request-handling code.

```rust
use djogi::prelude::*;
use sqlx::PgPool;

async fn list_invoices(
    State(pool): State<DjogiPool>,
    Extension(current_org): Extension<HeerId>,  // set by your auth middleware
) -> impl IntoResponse {
    let mut ctx = DjogiContext::from_pool(pool.clone());
    let invoices = atomic(&mut ctx, |tx| Box::pin(async move {
        // Set the tenant context — all queries in this transaction see only org's rows.
        tx.set_tenant(&current_org.to_string()).await?;

        Invoice::objects()
            .filter(|f| f.status().eq("open"))
            .order_by(|f| f.due_date().asc())
            .fetch_all(tx).await
    })).await?;

    Json(invoices).into_response()
}
```

Under the hood, `set_tenant()` executes:

```sql
SET LOCAL djogi.tenant_id = '8312847293';
```

`SET LOCAL` means the variable is scoped to the current transaction — it is cleared automatically when the transaction ends (commit or rollback). You cannot accidentally leak a tenant context between requests.

> **Warning:** Never call `SET djogi.tenant_id` without `LOCAL`. A session-level `SET` persists on the connection for the lifetime of the connection pool slot — if the connection is reused for a different tenant's request, the wrong tenant context will be active. Always use `djogi::set_tenant()` which uses `SET LOCAL`.

### Using `djogi::set_tenant()` in middleware

The standard pattern is a web-framework middleware layer that extracts the tenant from the authenticated session and injects it into the request. The example below uses Axum (enabled via the opt-in `axum` feature flag); the same pattern works for any other Rust web framework adopters wire in through its own per-framework feature flag (one flag per framework) or manual middleware.

```rust
// auth/middleware.rs — Axum example (requires the `axum` feature)
use axum::{extract::State, middleware::Next, response::Response};
use axum::http::Request;

pub async fn tenant_context_middleware<B>(
    State(pool): State<PgPool>,
    mut request: Request<B>,
    next: Next<B>,
) -> Response {
    // Your auth logic — extract org_id from JWT, session, API key, etc.
    let org_id: HeerId = extract_org_id_from_request(&request)?;

    // Inject into request extensions for handlers to use
    request.extensions_mut().insert(org_id);

    next.run(request).await
}
```

Individual handlers then start a transaction and set the tenant:

```rust
async fn create_invoice(
    State(pool): State<DjogiPool>,
    Extension(org_id): Extension<HeerId>,
    Json(input): Json<CreateInvoiceInput>,
) -> impl IntoResponse {
    let mut ctx = DjogiContext::from_pool(pool.clone());
    let invoice = atomic(&mut ctx, |tx| Box::pin(async move {
        tx.set_tenant(&org_id.to_string()).await?;

        Invoice::create(tx, Invoice {
            org_id,
            number: input.number,
            total_cents: input.total_cents,
            status: "open".into(),
            due_date: input.due_date,
            ..Default::default()
        }).await
    })).await?;

    Json(invoice).into_response()
}
```

## 4. `TenantScoped<T>`

`TenantScoped<T>` is a compile-level helper that wraps a model accessor and requires a tenant ID to be provided before any query can be issued. Use it in service layer code to make the tenant requirement explicit in the type signature.

```rust
use djogi::prelude::*;

pub struct InvoiceService {
    pool: DjogiPool,
}

impl InvoiceService {
    // The TenantScoped wrapper makes the tenant requirement part of the API signature.
    // You cannot accidentally forget to scope the query.
    pub async fn list_open(&self, scope: TenantScoped<Invoice>) -> djogi::Result<Vec<Invoice>> {
        let mut ctx = DjogiContext::from_pool(self.pool.clone());
        atomic(&mut ctx, |tx| Box::pin(async move {
            tx.set_tenant(&scope.tenant_id().to_string()).await?;

            Invoice::objects()
                .filter(|f| f.org_id().eq(scope.tenant_id()).and(f.status().eq("open")))
                .fetch_all(tx).await
        })).await
    }
}

// Caller must provide the tenant — cannot call the method without one
let scope = TenantScoped::<Invoice>::new(org_id);
let invoices = service.list_open(scope).await?;
```

## 5. `_insecurely()` Methods

Every terminal method on a tenant-scoped model has a corresponding `_insecurely()` variant that bypasses RLS enforcement. These are provided for legitimate administrative use — global statistics, support tools, data migrations, and cross-tenant reporting.

```rust
let mut ctx = DjogiContext::from_pool(pool.clone());

// Standard — enforces tenant isolation
Invoice::objects()
    .filter(|f| f.org_id.eq(org_id))
    .fetch_all(&mut ctx).await?;

// Bypasses RLS — sees all tenants' data
Invoice::objects()
    .fetch_all_insecurely(&mut ctx).await?;

// Specific per-terminal variants
Invoice::objects().fetch_one_insecurely(&mut ctx).await?;
Invoice::objects().fetch_optional_insecurely(&mut ctx).await?;
Invoice::objects().count_insecurely(&mut ctx).await?;
Invoice::objects().exists_insecurely(&mut ctx).await?;
```

**Every `_insecurely()` call is logged to the event log database with:**
- Caller function name (via `std::panic::Location`)
- Full stack trace
- The SQL query that was executed
- Timestamp and request ID (if in a request context)

**When `_insecurely()` is appropriate:**

- Admin panel displaying cross-tenant data to internal users
- Data migration scripts running outside request context
- Global analytics queries (total invoice count across all orgs)
- Seeding and testing infrastructure

**When `_insecurely()` is not appropriate:**

- Any code path that can be reached by an end user request
- Any query that should be filtered by tenant but you are not sure how to express it
- Shortcuts to avoid setting up `djogi::set_tenant()`

> **Warning:** The presence of `_insecurely()` in a production request handler is a critical security vulnerability. Every usage should be in clearly demarcated administrative code, wrapped in authorization checks that verify the caller is an internal admin, and reviewed during code review as a security-sensitive change. The audit log does not protect you — it only records what happened after the fact.

## 6. `DJOGI_ENV` Toggle

`DJOGI_ENV` controls the security mode of the running process.

| `DJOGI_ENV` value | Effect |
|---|---|
| `development` (default) | Relaxed logging, `db reset` allowed, `_insecurely()` calls logged but not alarmed |
| `production` | Schema snapshot signature required, `db reset` blocked, `_insecurely()` calls trigger immediate alerts via configured notification sink |

```bash
# Development (default)
DJOGI_ENV=development cargo run

# Production
DJOGI_ENV=production cargo run
```

In production mode, the framework performs additional startup checks:

1. `DJOGI_SIGNING_KEY` must be set — no unsigned schema snapshots accepted
2. `dev_mode = false` in `Djogi.toml` — schema is locked
3. `DATABASE_URL` must not resolve to `localhost` — enforced to prevent accidental prod-to-local confusion

## 7. `DjogiAuth` Trait

`DjogiAuth` is the extension point for swapping credential sources — database users, API keys, JWT claims, session tokens. Implement it on your application's credential type and register it with Djogi at startup.

The example below wires `DjogiAuth` against Axum's request type — enabled via the opt-in `axum` feature flag. Other Rust web frameworks integrate through their own per-framework feature flags (one flag per framework) and surface an equivalent `from_request` entry point against that framework's request type.

```rust
// DjogiAuth implementation — Axum example (requires the `axum` feature)
use djogi::auth::{DjogiAuth, Credentials, AuthError};
use axum::http::Request;

pub struct JwtCredentials {
    pub user_id: HeerId,
    pub org_id: HeerId,
    pub roles: Vec<String>,
}

impl DjogiAuth for JwtCredentials {
    fn from_request(req: &axum::http::Request<axum::body::Body>) -> Result<Self, AuthError> {
        let token = req
            .headers()
            .get("Authorization")
            .and_then(|v| v.to_str().ok())
            .and_then(|v| v.strip_prefix("Bearer "))
            .ok_or(AuthError::MissingCredentials)?;

        // Validate and decode your JWT here
        let claims = decode_jwt(token).map_err(|_| AuthError::InvalidCredentials)?;

        Ok(JwtCredentials {
            user_id: claims.sub,
            org_id: claims.org_id,
            roles: claims.roles,
        })
    }

    fn tenant_id(&self) -> Option<HeerId> {
        Some(self.org_id)
    }

    fn is_admin(&self) -> bool {
        self.roles.contains(&"admin".to_string())
    }
}
```

Register the implementation at startup:

```rust
// main.rs
djogi::auth::register::<JwtCredentials>();
```

With `DjogiAuth` registered, Djogi's middleware can automatically extract credentials from requests and enforce tenant context — without per-handler boilerplate.

## 8. Role Switching with `DjogiContext::set_role()`

Djogi supports Postgres role switching for fine-grained permission control. This is distinct from RLS — role switching changes which Postgres permissions apply, while RLS restricts row visibility. They can be used together.

```rust
use djogi::context::DjogiContext;

async fn admin_report(State(pool): State<DjogiPool>) -> impl IntoResponse {
    let mut ctx = DjogiContext::from_pool(pool.clone());
    let all_invoices = atomic(&mut ctx, |tx| Box::pin(async move {
        // Switch to the admin role — bypasses RLS policies that apply only to djogi_app role
        tx.set_role("djogi_admin").await?;

        Invoice::objects()
            .fetch_all_insecurely(tx).await
    })).await?;
    Json(all_invoices).into_response()
}
```

**Use role switching when:**

- You have database objects with permission grants tied to specific Postgres roles
- You need the database-level audit trail (Postgres logs) to reflect which role performed an operation
- You are managing schema objects that require elevated privileges

**Do not use role switching as a substitute for RLS.** RLS provides row-level isolation that persists even if the application has a bug. Role switching is a privilege mechanism, not an isolation mechanism.

## 9. Schema Snapshot Signing

`migrations/schema_snapshot.json` is the source of truth for the migration differ. If it is tampered with — accidentally or maliciously — the differ will not detect schema drift and may generate incorrect migrations.

In production, enable snapshot signing to detect tampering:

```bash
# Set a secret key — store in your secrets manager, not in code
export DJOGI_SIGNING_KEY="your-secret-key-here"
```

Every time `cargo djogi migrate` updates `schema_snapshot.json`, it also writes an HMAC-SHA256 signature of the file contents. On the next build, the build script verifies the signature before trusting the snapshot. If the signature does not match, the build fails with a clear error.

Verify the current snapshot manually:

```bash
cargo djogi verify
```

```
Verifying schema snapshot signature...
OK: schema_snapshot.json is authentic (signed at 2026-04-15T10:00:00Z)
```

If the snapshot has been tampered with:

```
ERROR: schema snapshot signature mismatch
  Expected: 8f3c2a1b...
  Found:    7e1d4f9c...

The schema snapshot may have been modified outside of `cargo djogi migrate`.
Do not run migrations until this is resolved.
Run `cargo djogi verify --explain` for details.
```

> **Warning:** In production deployments, `DJOGI_SIGNING_KEY` must be set. If it is not set and `DJOGI_ENV=production`, the framework refuses to start. This prevents accidental deployment of unsigned snapshots to production environments.

## 10. Security Anti-Patterns

The following patterns are common mistakes that compromise isolation, auditability, or correctness.

### Anti-pattern: Skipping `set_tenant()` and filtering manually

```rust
// WRONG — application-layer filtering is not defense in depth
let mut ctx = DjogiContext::from_pool(pool.clone());
Invoice::objects()
    .filter(|f| f.org_id.eq(org_id))
    .fetch_all(&mut ctx).await?;  // pool-backed ctx — no transaction, no RLS context
```

If the filter is accidentally removed, or if there is a bug in the org_id extraction, all tenants' data is exposed. The fix is to use `djogi::set_tenant()` so the database enforces isolation:

```rust
// CORRECT — RLS enforces isolation at the database level
let mut ctx = DjogiContext::from_pool(pool.clone());
atomic(&mut ctx, |tx| Box::pin(async move {
    tx.set_tenant(&org_id.to_string()).await?;
    Invoice::objects()
        .filter(|f| f.org_id().eq(org_id))  // belt-and-suspenders; RLS is the real guard
        .fetch_all(tx).await
})).await?;
```

### Anti-pattern: `_insecurely()` in request handlers

```rust
// WRONG — bypasses tenant isolation in a user-facing endpoint
async fn get_invoice(Path(id): Path<HeerId>, State(pool): State<PgPool>) -> impl IntoResponse {
    let mut ctx = DjogiContext::from_pool(pool.clone());
    let invoice = Invoice::objects()
        .filter(|f| f.id.eq(id))
        .fetch_one_insecurely(&mut ctx).await?;  // any user can access any org's invoice
    Json(invoice)
}
```

Any user who guesses or enumerates an invoice ID can access any organization's invoice. The fix is to set tenant context:

```rust
// CORRECT
async fn get_invoice(
    Path(id): Path<HeerId>,
    State(pool): State<DjogiPool>,
    Extension(org_id): Extension<HeerId>,
) -> impl IntoResponse {
    let mut ctx = DjogiContext::from_pool(pool.clone());
    let invoice = atomic(&mut ctx, |tx| Box::pin(async move {
        tx.set_tenant(&org_id.to_string()).await?;
        Invoice::get(tx, id).await  // RLS guarantees org isolation
    })).await?;
    Json(invoice)
}
```

### Anti-pattern: Committing secrets in `Djogi.toml`

```toml
# WRONG — never put secrets in Djogi.toml
[database]
url = "postgres://djogi:supersecretpassword@prod.db.example.com/myapp"
```

`Djogi.toml` is committed to version control. Every database credential, API key, and signing key belongs in environment variables or a secrets manager — never in a config file.

```toml
# CORRECT — non-secret configuration only
[database]
max_connections = 10
dev_mode = false
```

```bash
# Secrets in environment
export DATABASE_URL="postgres://djogi:$(vault read secret/db-password)@prod.db.example.com/myapp"
export DJOGI_SIGNING_KEY="$(vault read secret/djogi-signing-key)"
```

### Anti-pattern: Reusing a pool connection across tenant boundaries

```rust
// WRONG — SET LOCAL is transaction-scoped, but this misses that the pool reuses connections
#[djogi::deliberately_bypass_convention_with_raw_sql]
async fn batch_job(pool: &DjogiPool, tenant_ids: Vec<HeerId>) -> djogi::Result<()> {
    let mut ctx = DjogiContext::from_pool(pool.clone());
    for tenant_id in tenant_ids {
        // Issuing a session-level SET against a pool-backed context — no transaction boundary.
        // The SET persists on whichever connection the pool hands out, then leaks to the next
        // caller once this ctx releases it.
        ctx.raw_execute(
            "SET djogi.tenant_id = $1",
            &[&tenant_id.to_string()],
        ).await?;
        let _invoices = Invoice::objects().fetch_all(&mut ctx).await?;
    }
    Ok(())
}
```

Always use `djogi::set_tenant()` with a transaction-backed context, never a pool-backed one:

```rust
// CORRECT
async fn batch_job(pool: &DjogiPool, tenant_ids: Vec<HeerId>) {
    let mut ctx = DjogiContext::from_pool(pool.clone());
    for tenant_id in tenant_ids {
        atomic(&mut ctx, |tx| Box::pin(async move {
            tx.set_tenant(&tenant_id.to_string()).await?;  // SET LOCAL — clears on commit
            Invoice::objects().fetch_all(tx).await?;
            Ok(())
        })).await?;
    }
}
```

### Anti-pattern: Using `query_insecurely()` to avoid expressing the correct query

```rust
// WRONG — "I couldn't figure out the filter syntax so I bypassed it"
// Reaching for raw_query on a pool-backed context skips both
// the typed surface and the RLS / tenant guards in one move.
#[djogi::deliberately_bypass_convention_with_raw_sql]
async fn list_open_invoices_insecurely(ctx: &mut DjogiContext) -> djogi::Result<Vec<Invoice>> {
    ctx.raw_query::<Invoice>(
        "SELECT * FROM invoices WHERE status = 'open'",
        &[],
    ).await
}
```

The `raw_*` escape hatches exist for admin tooling and migrations — not as a workaround for query complexity. If you cannot express a query in `QuerySet`, push the gap upstream as a djogi issue rather than reaching for raw SQL.

```rust
// CORRECT — raw query inside an atomic() scope so RLS / tenant context apply
async fn list_open_invoices(
    ctx: &mut DjogiContext,
    org_id: HeerId,
) -> djogi::Result<Vec<Invoice>> {
    atomic(ctx, |tx| Box::pin(async move {
        tx.set_tenant(&org_id.to_string()).await?;

        // Under #[djogi::deliberately_bypass_convention_with_raw_sql]
        // on the enclosing helper if you really do need raw SQL.
        // See docs/spec/raw-sql-escape-hatches.md.
        Invoice::objects()
            .filter(|f| f.status().eq("open").and(f.org_id().eq(org_id)))
            .fetch_all(tx).await
    })).await
}
```
