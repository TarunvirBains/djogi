## 19. Resolved Design Decisions

| Decision | Resolution |
|---|---|
| Default PK type | HeerId — `BIGINT DEFAULT generate_id()`, database-native, time-ordered |
| HeerId ID pattern — default | `create()` uses `DEFAULT generate_id()` + `RETURNING id` |
| HeerId ID pattern — bulk | `HeerId::generate_many(n)` pre-allocates IDs before bulk INSERT |
| HeerId ID pattern — form | `HeerId::generate()` at form render time; INSERT with `ON CONFLICT DO NOTHING` |
| Serial PKs | Opt-in via `#[model(pk = Serial)]` |
| Node identity | NODE_ID environment variable; validated against heer_nodes at startup |
| HeerId JSON serialization | Always string — enforced by HeerId serde impl, no annotation needed |
| Datetime library | `time` crate — cleaner API, no CVE history |
| Framework fields (`id`, `created_at`, `updated_at`) | Macro-injected — real fields, not written by developer |
| `create()` input | Struct itself — no separate `CreateVehicle` wrapper |
| FK loading strategy | Explicit `.fetch()` or `.prefetch()` — no lazy loading |
| M2M strategy | Explicit through models required; `ManyToMany<T>` trait for convenience methods |
| M2M method naming | Explicit `RELATION` const — auto-pluralization is error-prone |
| M2M directionality | Each direction declared separately with its own `impl ManyToMany` |
| Shell async strategy | Dedicated tokio runtime + `block_on` per call — no `.await` in shell |
| Shell transactions | `begin()` / `commit()` / `rollback()` / `savepoint()` — explicit, always rollback on exit |
| Transaction timeout | Optional, developer-chosen at `begin()` — config `transaction_timeout_default` pre-fills prompt (default: 30m) |
| Power loss / crash | Postgres auto-rollbacks dropped connections — no manual recovery needed |
| Shell error handling | Print one-liner + save full traceback to `.djogi_shell_errors/`; session never unwound |
| Shell error log retention | 1 year default; configurable via `error_log_retention` in `Djogi.toml` |
| Shell verbose mode | `cargo djogi shell --verbose` — prints full tracebacks inline in addition to saving to disk |
| Shell history | `.djogi_history` gitignored; `scripts/` committed and shareable |
| Shell import/export | `.export`, `.import`, `.bookmark` — named Rhai scripts in `scripts/` |
| Shell headless execution | `cargo djogi shell --run scripts/name.rhai` — runs script without entering REPL |
| Query engine | Djogi-owned `SqlAccumulator` + `ConditionBuilder` — no third-party query builder |
| Raw escape hatch surface | Raw SQL remains available, but it is no longer an ordinary inherent-method convenience. The raw methods live behind the deliberate bypass harness; see the raw SQL harness decision below and [`raw-sql-escape-hatches.md`](./raw-sql-escape-hatches.md). |
| Raw SQL bypass harness | 2026-05-06: Raw SQL is treated as djogi's `unsafe`. In this repository's tests, use of `raw_*` requires the `#[djogi::deliberately_bypass_convention_with_raw_sql]` attribute and a syntactically attached `// JUSTIFICATION (djogi#<n>):` or `(PIN)` comment. Source-level `djogi::__bypass` references under `tests/` are banned. Tracked at GH #133. |
| CRUD log architecture | Separate `myapp_crud_logs` database; per-model mirror tables; delivery policy derived from a logging profile (`light`, `balanced`, `strict_audit`) with advanced overrides only as escape hatches |
| Event log architecture | Separate `myapp_event_logs` database; `tracing`-powered; severity-routed |
| Log database lifecycle | `db reset` wipes the application DB only — the CRUD-log and event-log databases survive every reset. Future `--wipe-crud-logs` / `--wipe-all-logs` opt-ins are a Phase 8+ concern; today the runner is single-context. |
| Logging UX | Profile-first configuration, not a matrix of operational knobs; maintainers should choose a profile and stop |
| Cross-database logging semantics | Djogi does not promise distributed atomic commit across app, CRUD-log, and event-log databases; stricter audit behavior is enforced by policy, not by pretending the databases commit atomically together |
| CRUD log failure policy | `light` = best-effort, `balanced` = durable bounded retry with health warnings, `strict_audit` = fail-closed for required audit writes |
| Event log failure policy | Best-effort by default under all built-in profiles; outages surface as warnings and metrics, not retroactive app-write failure |
| Admin console | Maahi — Dioxus full-stack on Axum, shipped as the `djogi-maahi` workspace crate behind the `admin` feature flag, mounted at `/_admin/` (see [`docs/spec/maahi/`](./maahi/index.md); HTMX + Askama was an earlier draft direction superseded by Phase 10 design) |
| Admin form generation | Auto-generated from `ModelDescriptor` — zero per-model UI code required |
| Admin validation | Auto-generated from field annotations + optional `impl AdminClean` hook |
| Admin M2M inlines | Auto-rendered from `impl ManyToMany<T>`; paginated, searchable, configurable |
| Admin opt-out | Per-model `#[model(admin = false)]`; per-field `#[field(expose(none))]` for the absolute field-hiding floor (never UI-rendered, even for superuser, even with `view_full_struct` / `write_full_struct`) per [Maahi — Field Visibility](./maahi/field-visibility.md). `#[field(admin_readonly)]` is a separate widget-render axis (visible but not editable). |
| `Jsonb<T>` in admin | Nested fieldset from schema; unknown fields shown read-only with raw JSON toggle |
| Seed script transactions | Phase 7 ships SQL seeds (`seeds/<database>/*.sql`) routed through `raw_ddl` — operators wrap statements in explicit `BEGIN` / `COMMIT` blocks when they want transactional rollback. The `djogi_seed_runs` ledger records seeds only after the body succeeds; a partial-apply leaves the ledger un-mutated so a re-run picks up where it left off. Rhai-based seeds are deferred to the Rhai shell phase. |
| Query builder — application code | Closure-based: `.filter(\|f\| f.field.gte(val))` — typed, composable, idiomatic |
| Query builder — shell / dynamic | Programmatic: `ModelFilter::new().field(Gte(val))` — serializable, no closures needed |
| Dirty tracking | Off by default; opt-in globally via `Djogi.toml` or per-model via `#[model(dirty_tracking)]` |
| FK cascade default | `RESTRICT` — safest Postgres default; overridden per-field with `#[field(on_delete = "...")]` |
| Field rename detection | `#[field(renamed_from = "old_name")]` — differ treats as rename not drop+add |
| Build drift diagnostic | Plain cargo warning — `build.rs` is diagnostic-only and never writes migration files |
| Migration generation | Explicit via `djogi migrations compose`; `build.rs` detects drift but does not mutate `migrations/` |
| Migration CLI surface | `djogi migrations compose/apply/rollback/status/verify/repair/baseline` are the canonical migration commands |
| Migration history attunement | `djogi migrations attune [target]` adjusts local migration-history Git state; it may fetch if needed, does not mutate the DB unless `--apply` is passed, and only updates the parent repo's submodule pointer with explicit `--record` or options that imply recording |
| Migration history squashing | `djogi migrations attune --squash` is dev-gated with the same safety contract as `djogi db reset` and must refuse on shared staging/production history |
| Schema snapshot | Updated only on successful `djogi migrations apply` — reflects actual DB state, never build state |
| Migrations folder | Git submodule — pipeline-managed, invisible to developer day-to-day |
| Migration down files | Always generated as a pair; data loss on destructive rollback documented in file |
| Migration runner | Djogi-owned on `tokio-postgres` / `deadpool-postgres` — no `sqlx::migrate` compatibility layer |
| Migration ledger table name | `djogi_schema_migrations` |
| Migration advisory lock key | Hash-derived per target: `SHA-256("djogi:migrations:<target-name>")`, first 8 bytes as big-endian `i64` (Phase 7 v3 OQ-06 ruling 2026-04-23). Multi-target = multi-lock; no shared literal, no collision surface with other applications. |
| Migration advisory lock connection | Dedicated non-pooled `tokio_postgres::Client` per operation; the lock holder must own the session for the full `apply` / `rollback` / `repair` window. Pooled connections cannot hold session advisory locks — pool reuse would silently swap the lock holder (Phase 7 v3 §3 ruling 2026-04-23, Codex P0-05 fix). |
| Migration file-level workspace lock | `fcntl` `LOCK_EX` on `<workspace-root>/.djogi-migrations-lock` held exclusively for the duration of `compose` / `attune` / `apply` / `repair` / `baseline`. 30s timeout; D025 on contention. Protects local file state (pending snapshots, `git mv`) that the DB advisory lock does not cover (Phase 7 v3 §6 addition 2026-04-23, Codex P1-06 fix). |
| Migration checksum format | SHA-256 over normalized SQL bytes, stored as `V1:` + lowercase hex digest. Normalization = BOM strip + `\n` line endings + single trailing newline **only** — comments and trailing whitespace are preserved in the hash (Phase 7 v3 Codex P1-04 fix 2026-04-23) so edited review comments surface as drift on `verify`. |
| Migration rollback order | Reverse ledger insertion order (`id` descending), not version-string order |
| Out-of-order migration policy | local/dev allow + warn + record; CI/prod reject by default; override requires explicit flag |
| Three-file snapshot lifecycle | `target/djogi_models.json` (every `cargo build`) → `target/djogi_pending/<target>/<app>.json` (`djogi migrations compose`) → `migrations/<target>/<app>/schema_snapshot.json` (post-successful `apply`). `build.rs` three-way match per (target, app) pair per Phase 7 v3 OQ-10 ruling 2026-04-23. |
| Snapshot `format_version` field | `"1"` at initial ship. Exact string match on load; unknown versions fail fast with a clear upgrade message. Bump only on breaking shape changes; additive fields do not bump (Phase 7 v3 §6 ruling 2026-04-23). |
| Apps subsystem placement | Ships in Phase 7-Zero T7–T10 (per OQ-07 ruling 2026-04-23, reversing the earlier "apps = Phase 7 proper" default). The `djogi::apps!` macro, `AppRegistry`, `AppDescriptor`, lifecycle markers (`renamed_from`, `tombstone`, `moved_from_app`), and the cross-app FK graph are Phase 7-Zero deliverables; Phase 7 consumes them as frozen contracts. |
| Apps declaration syntax | Type-path via unit structs, not string labels. `djogi::apps! { #[app(database = "main")] pub struct Vehicles; }` + `#[model(app = Vehicles)]`. Rust name resolution + sealed `App` trait bound enforce declaration at compile time; undeclared / non-app types fail with standard rustc errors. No cross-crate inventory lookup at macro expansion time (Phase 7-Zero v3 §4B, Codex P0-03 fix 2026-04-23). |
| App identity | `(database, label)` pair, not label alone. Two apps with the same label in different databases are legitimate — `main/audit/` and `crud_log/audit/` are distinct migration directories. Compile-time (same-invocation) and runtime (cross-invocation) uniqueness checks both enforce the pair. `CrossAppEdge` and `AppIdentity` carry both fields. (Phase 7-Zero v3 T7 fixup #3 ruling 2026-04-23.) |
| Apps seal enforcement | Convention at compile time, verified at migration time. True hard-sealing of a proc-macro-emitted trait is not achievable in stable Rust when the macro lives in a separate crate — every pub path the macro reaches is downstream-reachable too. `djogi::apps::__DJOGI_APPS_SEAL_TOKEN` is `#[doc(hidden)] pub`; a determined downstream crate can hand-write `impl djogi::App for Fake` and compile, but the forged impl is inert. Phase 7's migration differ cross-checks every `#[model(app = X)]` against `AppRegistry::all()` at `djogi migrations apply` startup and rejects unregistered apps before any SQL executes. (Phase 7-Zero v3 T7 fixup #4 ruling 2026-04-23.) |
| PK-type flip classification | Native Phase 7 work (`SchemaDelta::Classification::PkTypeFlip`), shipped as Phase 7 T9. Distinct from `RequiresLivePlan`, which is reserved exclusively for operator-driven column-level compatibility-window rollouts consumed by Phase 7.5. Rationale: HeeRanjId identity is Djogi's raison d'être; FK-cascading PK migrations are core migration-engine work, not a staged-rollout layer above it (Phase 7 v3 OQ-09 ruling 2026-04-23 + Codex P0-01 fix). |
| Online-safety classification enum (Phase 7.5) | Four variants — `OnlineSafe` (no live plan), `FastLockDestructiveGuarded` (short-lock but destroys data / invalidates dependents; gated by `--allow-destructive`), `ExpandContract` (Phase 7.5 live plan via `RequiresLivePlan` handoff), `OfflineOnly` (refused). `DROP COLUMN` is `FastLockDestructiveGuarded`, not `OnlineSafe`. Volatile defaults downgrade column-add from `OnlineSafe` to `ExpandContract`. Postgres-18-fast-path rows are hard dependencies, not optional optimizations (Phase 7.5 v3 §7 ruling 2026-04-23, Codex P1-01 fix). |
| Concurrent index creation | Deterministic A (Phase 7-Zero v3 Q1 ruling 2026-04-22). `concurrently = true` at declaration sets `IndexSpec::requires_out_of_transaction = true`; runner emits `CREATE INDEX CONCURRENTLY` in every profile (prod, CI, dev, test); containing migration is non-transactional in every profile. No profile-gated behavior. Framework does not auto-detect — operator responsibility. Apply-time advisory warning (Phase 7-Zero v3 §6.5) surfaces the foot-gun without changing DDL. |
| Unique constraint vs unique index default | Unique constraint is the default for ordinary uniqueness. Unique index only when Postgres requires it: partial (`predicate`), expression-target, `include`, or `nulls_not_distinct = true`. The macro picks; user does not have to know the distinction for common cases (Phase 7-Zero v3 §2 item 2 + §6.1 lowering rules). |
| Index column ordering | Column order is semantic — preserved byte-for-byte in descriptor, SQL, canonical name, and diff. Never sorted. `index(fields = [last, first])` and `index(fields = [first, last])` are different indexes with different names (Phase 7-Zero v3 §2 item 3). |
| Index column spec | Per-column opclass + sort direction + nulls ordering via `IndexColumnSpec { name, opclass, order, nulls }` on `IndexTarget::Columns(&[IndexColumnSpec])`. `IndexColumnSpec::simple(name)` const-fn constructor keeps the common case ergonomic. Top-level `IndexSpec::opclass` is removed — per-column opclass supersedes it (Phase 7-Zero v3 §4, Codex P1-02 fix 2026-04-23). |
| Index predicate validation | Raw SQL fragment (e.g. `"deleted_at IS NULL"`); Djogi does not parse or shape-validate predicates. Postgres parses at migration time; invalid SQL surfaces as a migration error with the full server-side diagnostic. No regex, no DSL (Phase 7-Zero v3 §3, Codex P0-04 fix 2026-04-23). |
| `djogi migrations attune --squash` publication flag | `--publish` (not `--push`). Abstraction consistency with `attune` (both djogi verbs, not mixed with git vocabulary); communicates the consequence (team sees the rewrite) rather than the mechanism; matches `cargo publish` ecosystem vocabulary (Phase 7 v3 OQ-04 ruling 2026-04-23). |
| `djogi docs` output layout | One Markdown file per registered model under `<output>/<app>/<Model>.md`, plus a top-level `<output>/README.md` index grouped by app (sorted alphabetically; the synthetic global bucket appears under the on-disk token `_global_`). Output is byte-deterministic against the same descriptor inventory — no embedded timestamps or environment-derived data — so two runs against the same compiled binary produce identical files. Default output root: `target/djogi-docs/`. (Phase 7 T8 ruling 2026-04-25.) |
| Composite migration boundary | Composite unique constraints and composite indexes are in `0.1.0`; composite primary keys are not |
| Multi-database migration contract | Migrations are target-scoped at the ledger and advisory-lock layers: each database target has its own `djogi_schema_migrations` ledger (one per target, shared across all apps in that target) and its own advisory-lock namespace (per "Migration advisory lock key" row above). Snapshots are finer-grained — per `(target, app)` per the "Three-file snapshot lifecycle" row — but each target's snapshot set is still independently-governed. Djogi does not promise distributed atomic migration across targets. |
| Cross-database foreign keys | Explicitly rejected — ORM `ForeignKey<T>` is same-database-target only; cross-target references must be scalar/application-level references |
| Database target | Postgres only — permanent decision, not a limitation; enables JSONB, HeeRanjId, advisory locks, transactional DDL, `RETURNING` |
| Postgres version floor | Postgres 18 — no support for older versions. Rationale: Djogi is pre-publish and unapologetic about adoption shape; teams migrating an existing app to Djogi have substantial app-side work regardless, so bundling a Postgres upgrade is a small marginal cost. The framework will freely use any Postgres 18+ feature (extended protocol niceties, latest JSONB work, `MERGE`, logical replication, generated-column expressiveness) without version-gating fallbacks. |
| Dev database reset | `djogi db reset` — triple-gated: localhost-resolving `DATABASE_URL`, `Djogi.toml::profile != "production"`, and explicit confirmation (`--yes` flag or interactive `yes` answer). Drops + recreates the application DB through the maintenance database (`postgres` by default; overridable via `--maintenance-database`), then replays committed migrations through the runner's normal `apply_plan` path. Logging databases are NOT touched. (Phase 7 T8 ruling 2026-04-25.) |
| CLI interface | `djogi` CLI — installed via `cargo install djogi-cli` |
| Djogi's scope | Model derivation chain only — does not duplicate `tokio-postgres`, HeeRanjId, Tokio, or any Rust web framework's responsibilities. `axum` is the best-covered framework example today (opt-in via the `axum` feature flag); other frameworks integrate through their own per-framework flags or manual wiring. |
| Public requirement translation | Private app requirements may inform Djogi, but specs/docs describe them only as product-agnostic framework capabilities |
| Core vs companion crate boundary | Djogi keeps reusable data-layer primitives; domain policy, workflow logic, and specialized integrations belong in app crates or companion crates |
| `Jsonb<T>` field type | `JSONB` column with typed schema, serde deserialization, validator validation, nested schema support |
| Unknown field preservation | Fields not in schema loaded into `extra: IndexMap<String, UnknownField>` — never dropped on save |
| `UnknownField` variants | `String`, `Bool`, `Float`, `Int`, `Null`, `RawJson` — no implicit coercion between types |
| `UnknownFieldError` | `FieldNotFound`, `TypeMismatch`, `NoImplicitCoercion` — all conversions return `Result` |
| Nested `Jsonb<T>` | Fully supported — each nesting level has its own typed schema and unknown field boundary |
| JSONB subfield queries | Typed filter accessors generated per known field using Postgres JSONB path operators |
| CRUD logging | Optional per-model or global; stored as per-model `{snake_case(model)}_logs` mirror tables in the separate `myapp_crud_logs` database (see [Logging](./logging.md) §9.1); off by default (a single shared `_djogi_crud_log` table was an earlier draft direction superseded by the per-model mirror layout) |
| CRUD log JSON diffing | Dot-notation paths through full `Jsonb<T>` nesting depth including unknown field changes |
| CRUD log actor | Optional `save_with_actor()` or request-context hook; null if not provided |
| Project scaffolding | `djogi new` — scaffolds project and initializes migrations submodule |
| Regex anywhere in djogi (Rust side) | **No Rust regex engine, ever — no exceptions.** No regex-engine dependency (`regex`, `regex-lite`, `fancy-regex`, `regex-automata`, or equivalent) may enter any workspace crate (`djogi`, `djogi-macros`, `djogi-cli`, `djogi-shell`, or any future crate). Framework-internal pattern checks (identifier validation, DDL emission shape checks, anything Djogi enforces at compile or migration time) are expressed in plain English and implemented with stdlib byte primitives: `u8::is_ascii_alphabetic`, `u8::is_ascii_alphanumeric`, explicit byte equality, sorted const slices with `binary_search`, stack-allocated `[u8; N]` buffers, and similar — never via regex notation in doc comments, commit messages, or other in-repo text. Regex is heavy, hides intent behind a DSL most readers re-parse every time, and invites per-query allocation; that critique applies to *Rust-side* regex use, which the rule still bans absolutely. Regex notation in prose is no easier to skim than the underlying rule written out — spell the rule out in words (e.g. "ASCII letter or underscore followed by ASCII alphanumerics or underscores, up to 63 bytes"). |
| Postgres POSIX regex operators (carve-out) | **Permitted as a Postgres feature.** Postgres exposes POSIX regex matching as the `~` and `~*` SQL operators; Djogi surfaces them through the typed query API as `FieldRef::regex(s)` (`col ~ $1`) and `FieldRef::iregex(s)` (`col ~* $1`), and through the programmatic builder as `Lookup::Regex(String)`. The carve-out is narrow and deliberate: the predicate runs entirely server-side, no Rust regex code is linked, and the adopter is composing a Postgres query — not invoking framework-internal regex. The carve-out covers only the `~` / `~*` operators reached through the typed surface or `ctx.raw_*`; framework-internal text matching never reaches for regex even where Postgres supports it. |
| Spatial SRID | Locked to `GEOGRAPHY(Point, 4326)` in Phase 6. Non-4326 work goes through raw SQL (`ctx.raw_execute(...)`) combined with `FieldSqlType::Custom(&'static str)` on the field type. A future `GeoPoint<const SRID: u32>` generalization is a candidate if real adoption pressure emerges — it would be an additive, non-breaking change per the pre-publish policy. |
| Spatial codec | Manual EWKB encode/decode in-repo (`djogi/src/geo/ewkb.rs`) — 25-byte little-endian layout (endian marker, type word with SRID flag, SRID, X longitude, Y latitude). No new dependency. A future dep swap to `geozero` or equivalent is a single-file change because all raw-byte logic is isolated in `ewkb.rs`. |
| Spatial feature-flagging | `spatial` feature flag on the `djogi` crate (not a separate crate, per the one-djogi-crate rule). Default builds do not compile any PostGIS surface. The `djogi::geo` module and the `djogi::GeoPoint` re-export are both gated on `#[cfg(feature = "spatial")]`. |
| Spatial query IR | `SpatialExpr` nodes live under Phase 4's `ExprNode` enum as a single `ExprNode::Spatial(SpatialExpr)` variant. No parallel `Condition::Spatial` arm. This keeps filter, order, annotate, and aggregate pipelines on one emitter walk. |
| Spatial ordering determinism | `order_by_distance` appends the primary-key column (`id`) as an unconditional ascending tiebreak. Equidistant rows sort by ascending primary key — reproducible across repeated executions and safe for keyset pagination. |
| Non-point spatial geometries (Phase 6.5) | `GeographyValue` trait is sealed; ships concrete impls for `GeoPoint`, `LineString`, `Polygon`, `MultiPoint`, `MultiLineString`, `MultiPolygon`. Each has a manual EWKB codec isolated in `djogi/src/geo/ewkb.rs` — no new dependency. OGC simple-feature invariants (closed rings, minimum-point counts) validated at constructor time; `postgres_types::{ToSql, FromSql}` impls route through the same EWKB layer. |
| Spatial shape-predicate cast discipline (Phase 6.5) | `ST_Intersects` has a native `geography` overload, so Djogi emits `ST_Intersects(<col>, $n::bytea::geography)` with no column cast. `ST_Contains` / `ST_Touches` / `ST_Within` have no geography overload in PostGIS 3.x, so both sides are cast to `geometry`: `ST_<Func>(<col>::geometry, $n::bytea::geometry)`. The `$n::bytea::<type>` double-cast is required because `Vec<u8>: ToSql` binds as `bytea`; a direct `$n::geography` cast makes `tokio_postgres` prepare `$n` as `geography` and reject the `Vec<u8>` value at prepare time. |
| Spatial region-JOIN function choice (Phase 6.5) | `group_by_region` / `count_by_region` emit `LEFT JOIN … ON ST_Covers(r.<r-geo-col>, t.<t-geo-col>)` — not `ST_Contains`. Two reasons: (1) `ST_Covers(geography, geography)` exists in PostGIS 3.x, `ST_Contains(geography, geography)` does not, so `ST_Covers` avoids `::geometry` casts under the JOIN and keeps GiST-indexed bbox prefiltering active on the geography column; (2) `ST_Covers` is boundary-inclusive (a point on a polygon's edge is "covered") whereas `ST_Contains` is interior-only (the same edge point is "not contained"). The two functions agree for points strictly inside or outside the polygon and differ only on the boundary — and for spatial grouping, the boundary-inclusive interpretation is the useful one: a point on a neighborhood edge should still count under *some* neighborhood rather than falling into the `None` bucket. |
| Spatial cluster emitter subquery wrap (Phase 6.5) | `cluster_by_proximity` wraps the `ST_ClusterDBSCAN(...) OVER ()` call in an inner `FROM (SELECT t.*, ...) AS t` subquery so the outer `GROUP BY cluster_id` references a materialised column. The flat form `SELECT ST_ClusterDBSCAN(...) OVER () AS cluster_id ... GROUP BY cluster_id` is rejected by Postgres with `ERROR: window functions are not allowed in GROUP BY`. |
| Spatial grouping source enum (Phase 6.5) | The three spatial grouping shapes (Join / Cluster / Geohash) unify under a single `SpatialGroupSource` variant on `GroupedAnnotatedQuerySet`. Dispatch to the appropriate SQL builder happens in `build_grouped_annotated_select`. New shapes are added as new variants — the grouped-substrate contract (key-tuple emission, aggregate-tuple emission, HAVING / ORDER / LIMIT tail) is identical across all three. |
| Grouped queryset type-state (Phase 6.5) | Grouping transitions through three type-states: `QuerySet<T>` → `GroupedQuerySet<T, K>` (via `group_by` / `rollup` / `cube` / `group_by_sets`) → `GroupedAnnotatedQuerySet<T, K, A>` (via `.annotate(...)`). Each stage locks in what downstream operations are allowed — you cannot fetch a `GroupedQuerySet` without first annotating, you cannot call `group_by` on an already-grouped queryset. The sealed `IntoGroupKeyTuple` and `IntoAggregateTuple` traits cover arity 1–4 in this phase; exceeding the cap raises a clear compile error. |
| Window aggregate without `group_by` (Phase 6.5) | `.annotate(...)` on a plain `QuerySet<T>` emits the aggregate with `OVER ()`, producing one row per base table row with the table-wide aggregate attached. `.annotate(...)` after `group_by` omits the `OVER` clause and emits a plain `GROUP BY` aggregate. One method, two emission modes keyed on type-state — no separate `.window(...)` entry point. |
| Aggregate alias discipline (Phase 6.5) | Aggregates are aliased `__djogi_agg_N` (N starting at 0). User-supplied SELECT aliases that collide with the synthetic alias are caught at SQL-build time by `assert_no_alias_collision()` (the generic SELECT-list duplicate-alias detector at `djogi/src/query/sql.rs:1559`), which returns `DjogiError::AliasCollision { alias }`. The check is generic across any duplicate alias; it indirectly enforces the `__djogi_agg_*` reservation because the framework always emits the synthetic alias and a user duplicate would surface as a SELECT-list collision. The synthetic alias prevents user renames from breaking positional decode. |
| `#[djogi_test(extensions = [...])]` (Phase 6.5) | The test harness macro accepts an `extensions = ["..."]` array. Each per-test database runs `CREATE EXTENSION IF NOT EXISTS "<name>"` after HeeRanjID install and before user setup. Extension names validated with a byte-level ASCII-identifier check — no regex (per the no-regex rule), no database round-trip for validation. Invalid names fail at macro expansion with a span-precise `syn::Error`; valid-but-nonexistent extensions surface as `DjogiError::Db` at runtime. |
| Two-phase constraint validation default (Phase 7.5) | `CHECK`, `NOT NULL`, and `FOREIGN KEY` constraints added to tables exceeding `live.validation_threshold_rows` (default 100k) are emitted as `ADD CONSTRAINT … NOT VALID` followed by a separate `VALIDATE CONSTRAINT` step. The `NOT VALID` step takes a fast catalog lock; `VALIDATE` runs under `ShareUpdateExclusiveLock` (concurrent reads + writes allowed). Operator drives the validation step via `djogi live finalize`. Below the threshold, single-statement validation continues for ergonomic small-table behavior. **Exclusion constraints are not eligible** — Postgres 18 does not accept `NOT VALID` for `EXCLUDE …` constraints, so adding an exclusion constraint to a populated table classifies as `OfflineOnly` (operator must accept the `AccessExclusiveLock` window or rebuild via the unique-via-index pattern when the constraint reduces to uniqueness). **Lens:** scalability — large-table validation for the supported constraint kinds no longer blocks production; production stability — `AccessExclusiveLock` window collapses to milliseconds for CHECK / NOT NULL / FK; never emits SQL Postgres rejects. |
| Unique constraint via concurrent index promotion (Phase 7.5) | When adding a unique constraint to a populated table classified `ExpandContract`, the live plan emits `CREATE UNIQUE INDEX CONCURRENTLY` then `ALTER TABLE … ADD CONSTRAINT … USING INDEX`. The promotion `ALTER` takes a brief `AccessExclusiveLock` (sub-millisecond on Pg18); the index build runs lock-light. Same shape applies when the differ produces a `DROP INDEX` + `CREATE INDEX` pair on overlapping columns: both sides must be `concurrently = true` or the operation refuses. **Lens:** scalability — uniqueness enforcement on large tables no longer requires downtime; production stability — index-replacement no longer leaves the table without an index window. |
| Three-step column-with-default add (Phase 7.5) | Postgres-VOLATILE `DEFAULT` expressions (`clock_timestamp()`, `random()`, `gen_random_uuid()` — the formal `VOLATILE` category that Pg18's fast-path explicitly does NOT cover) route through a 3-step live plan: (1) `ADD COLUMN … NULL` + install a write-side trigger that populates the column for INSERTs / UPDATEs landing during the window, (2) `ALTER TABLE … ALTER COLUMN … SET DEFAULT <expr>` so new rows get the default natively, (3) chunked backfill of historical rows via the standard backfill substrate. Stable / immutable defaults — including `now()`, `CURRENT_TIMESTAMP`, `transaction_timestamp()` (all formally STABLE), string / integer literals, and immutable function calls — remain `OnlineSafe` (catalog-only on Pg18). Postgres `DEFAULT` clauses cannot reference other columns; that requirement falls out of scope for this row and routes through generated columns or a custom transform instead. **Volatility resolution is compose-time and host-independent:** Djogi ships a static table of every Pg18 built-in function's `provolatile` category baked into the classifier (`djogi/src/migrate/pg_volatility.rs`); unknown identifiers — user-defined functions, extension functions, qualified `schema.func` calls Djogi can't classify — default conservatively to `VOLATILE` and route through 3-step staging. Adopters with a known-stable user-defined function can override via `#[field(default_volatility = "stable")]`. The classifier never reads live `pg_catalog`; compose remains pure and host-stable, so a UDF installed on staging but not production produces the same plan on every host. **Lens:** scalability — never rewrites the table in place when staging is needed; production stability — host-independent classification eliminates a class of "works in staging, blocks in production" surprises; correctness — only emits patterns Postgres accepts; simplicity — one static table, one explicit override knob. |
| Per-migration timeouts (Phase 7.5) | Every migration session sets `statement_timeout` and `lock_timeout` at the start of work and restores at the end. Defaults locked: `statement_timeout = 1h`, `lock_timeout = 2s`. `lock_timeout = 2s` deliberately favors refusal over indefinite queueing — a stuck migration that holds `AccessExclusiveLock` past 2s gets rejected, freeing the table for production traffic. Per-migration overrides via header pragmas (`-- djogi: statement_timeout=10m`); per-project defaults via `Djogi.toml` `[live] statement_timeout` / `lock_timeout`. **Lens:** production stability — bounded blast radius on every migration; simplicity — one defensible default everywhere. |
| Exponential lock-retry on contention (Phase 7.5) | When a migration session is refused due to `lock_timeout`, the runner retries with exponential backoff. Default policy: 4 attempts at 1s/2s/4s/8s initial delay (configurable via `[live] lock_retry_attempts` / `lock_retry_initial_ms`). Eliminates spurious failures from brief lock contention without masking persistent contention. Retry only on `lock_timeout`-class errors; other failures abort immediately. **Lens:** production stability — operator no longer manually re-runs on transient contention; simplicity — one tuning knob for the rare case. |
| Justification ledger field for destructive operations (Phase 7.5) | When `--allow-destructive` is passed to `djogi migrations apply` or any command emitting `Lossy` / `Destructive` SQL, `--justify "<reason>"` is required and persisted in `djogi_schema_migrations.justification` (TEXT, NOT NULL when the row's classification is destructive). The same gate applies at the live-plan level: any plan whose step graph contains a destructive step requires `--allow-destructive --justify` at `djogi live run` time, and the justification is copied into every ledger row that step ultimately produces. For `attune --record` of hand-edited migrations containing detected dangerous statements, the justification is stored as a `-- djogi-justify: <reason>` header in the migration file itself at record time (since `attune --record` does not mutate the live DB) and copied into the ledger when the migration is later applied. No silent destructive operations; every destructive ledger row carries an audit-trail reason regardless of which path produced it. **Lens:** production stability — every destructive change is reviewable post-incident, no matter which command surfaced it; simplicity — one flag, one column, one persistence path; correctness — `attune --record` doesn't pretend to write to a ledger it has no business mutating. |
| Backfill side-effect suppression default (Phase 7.5) | While a live-plan `BackfillChunked` step writes rows, `#[model(events)]` outbox emission and other framework write-hooks are suppressed by default. Backfilling 1M rows must not fan out 1M domain events to downstream consumers. Opt-in restoration via `#[migration(emit_events_during_backfill)]` on the migration definition or the `--emit-events` CLI flag. The suppression is scoped to the live-plan step's transaction; ordinary application writes outside the migration session are unaffected. **Lens:** scalability — prevents event-storm on large backfills; production stability — downstream consumers don't receive synthetic schema-change traffic. |
| Hash-index hazard refusal (Phase 7.5) | The classifier refuses `IndexType::Hash` declarations that don't have `requires_out_of_transaction = true` set, with a `IndexBuildHazard::HashRequiresConcurrent` diagnostic at compose time. Hash indexes have transactional limitations on Pg18 (cannot be built inside a transaction in some configurations) that bite operators silently otherwise. Already-present hash indexes in the live DB are not affected. **Lens:** production stability — eliminates a class of foot-gun before SQL ever runs. |
| Multi-FK staging threshold (Phase 7.5) | When a single `(database, app)` bucket diff produces 4+ `ADD CONSTRAINT … FOREIGN KEY` operations or 4+ `DROP CONSTRAINT` operations targeting FKs on a single table, classification escalates to `ExpandContract` and the live plan stages them across multiple steps with interleaved `VALIDATE CONSTRAINT` calls. Threshold (default 4) configurable via `[live] multi_fk_threshold`. Same threshold applies to dropping a table with 4+ inbound FKs — but the trailing `DROP TABLE` step retains its destructive classification and requires `--allow-destructive --justify "<reason>"` independently of the staging plan. The orthogonality is structural: `ExpandContract` describes *how* steps are sequenced; destructive gating describes *what* approvals each step needs. A live plan whose graph contains any step emitting `Destructive` or `Lossy` SQL must be invoked with both gates passed at the plan level. **Lens:** scalability — prevents lock-storms on heavily-referenced tables; production stability — bounded lock concurrency *and* destructive operations cannot smuggle past gating by hiding inside a live plan. |
| Stored generated column rewrite classification (Phase 7.5) | Adding or changing a `GENERATED ALWAYS AS (<expr>) STORED` column on a populated table rewrites every row under `AccessExclusiveLock` — and creating the *replacement* generated column also rewrites the table, so a shadow-column pattern does NOT save the operator from the lock window. Classified `OfflineOnly` for populated tables; operator must accept the maintenance window or migrate the column to a regular column with an application-level fill (which routes through the 3-step column-with-default pattern instead). Virtual generated columns (Pg17+) are catalog-only and remain `OnlineSafe`. Replacement-column expand/contract still applies if the operator chooses to remodel the column away from STORED-generated entirely; that's a regular column transition. **Lens:** correctness over wishful thinking — Djogi does not pretend to make table-rewrite-required DDL online when Postgres semantics make that impossible; production stability — the `OfflineOnly` refusal forces operator acknowledgement instead of a silent multi-minute lock. |
| `check_down` opt-in for down-migrations (Phase 7.5) | Down-migrations run through the same `OnlineSafety` classifier when `[live] check_down = true` is set in `Djogi.toml` (default: `false`). High-stakes deployments opt in; default-off keeps dev rollback ergonomic. When enabled, `djogi migrations rollback` refuses the rollback if the down-migration emits `Destructive` / `Lossy` SQL without `--allow-destructive --justify`. **Lens:** production stability — destructive rollbacks get the same gating as forward changes for teams that want it; simplicity — opt-in keeps default behavior unchanged. |
| Live plan multi-app boundary (Phase 7.5) | A single live plan operates within one `(database, app)` bucket — same boundary as Phase 7's per-target advisory lock. Cross-app live plans are refused at compose time. When a single descriptor diff legitimately spans multiple buckets, Phase 7's compose phase splits it per-bucket and Phase 7.5 materializes one independent plan per bucket; ordering between those plans is the operator's responsibility (each plan is run via its own `djogi live run <plan-id>` invocation, and the operator decides the sequence). Plan-to-plan dependency machinery is out of scope for v1 — operators with strict ordering needs use shell scripts or per-environment runbooks. The `djogi_live_plans` table carries `target_database` + `app_label` columns for bucket scoping. **Lens:** scalability — per-bucket lock semantics carry forward from Phase 7; simplicity — operator-driven ordering keeps Djogi out of the "build a workflow engine" business until adoption pressure surfaces a concrete need. |
| Three-DB live-plan applicability (Phase 7.5) | Event-log database evolves via Phase 7 migrations directly — no `ExpandContract` paths, no operator-driven rollouts; event-log writes are best-effort under all built-in profiles per the existing `Event log failure policy` row, so brief `AccessExclusiveLock` windows there don't block production. **Crud-log database respects the active CRUD logging profile.** Under `light` and `balanced` profiles (best-effort + bounded retry), crud-log migrations route directly to Phase 7 the same way event-log does. Under `strict_audit` (fail-closed), crud-log migrations on populated tables route through Phase 7.5's classifier the same way the application DB does — because under fail-closed semantics, a multi-second `AccessExclusiveLock` on a crud-log mirror table blocks every `INSERT` / `UPDATE` / `DELETE` against the corresponding application table. The classifier inspects both `target_database` and the resolved logging profile. **Lens:** production stability — fail-closed audit guarantees aren't undermined by direct-mode log-DB migrations; simplicity — adopters who chose `strict_audit` get safe migration semantics for free; correctness — the classifier respects the audit contract Djogi already promises. |
| PK-flip vs online-safety classifier boundary (Phase 7.5) | `Classification::PkTypeFlip` is **not** routed through the online-safety classifier. PK-flip migrations are inherently long-running and unavoidably touch every cascading FK; their orchestration lives in Phase 7 T9 with the cascade emitter family. The online-safety dimension applies only to column-level operations on tables not undergoing PK-flip. Phase 7.5's `RequiresLivePlan` handoff and `PkTypeFlip` are mutually exclusive — a single delta cannot carry both classifications. **Lens:** simplicity — one orchestration owns PK-flip end-to-end; production stability — no double-routing of PK-flip work. |
| Custom-PK-type flip support (Phase 7.5) | Phase 7 T9 ships PK-flip emitters for the four built-in HeeRanjId variants (`HeerId`, `HeerIdRecencyBiased`, `RanjId`, `RanjIdRecencyBiased`). Phase 7.5 extends the emitter family to support custom PK types declared via `djogi::primary_key!` (Phase 7-Zero-2 surface). The descriptor diff already detects the flip; Phase 7.5 adds the `CustomPkFlip` cascade emitter that the `Classification::PkTypeFlip { kind: Custom }` variant routes through. Validation: custom PK kinds must declare `flip_to: &[CustomPkKind]` in their macro definition listing legal flip targets. **Lens:** scalability — adopters with HeeRanjId-incompatible identity needs aren't locked out of online flips; idiomatic Rust — sealed-trait extension preserved end-to-end. |
| Visage compat-window contract (Phase 7.5) | During `ExpandContract` compatibility windows, visage `SELECT` projections (Phase 4.5 / Phase 7-Zero-2) are pinned to the *contracted* schema (post-cutover column set). Adopters running queries during the compat window that need the legacy projection must opt in via `#[visage(during_migration = legacy)]` on the visage definition. Default is forward-looking so post-cutover queries don't surprise. The `DjogiVisageOf<M>` boundary (Phase 7-Zero-2) carries the migration-aware projection through the compile-time contract. **Lens:** production stability — query shape doesn't shift on cutover for the default case; simplicity — one knob for the rare opt-in. |
| Backfill resume substrate scope (Phase 7.5) | Resume-on-restart for backfills is two-tier: (tier-1) **operator-driven** via `djogi live resume <plan-id>` — single-process, no daemon, picks up at `backfill_rows_done`, can advance through any plan step including operator checkpoints (`CutoverReads`, `CutoverWrites`, `FinalizeConstraints`); (tier-2) **daemon mode** via `djogi live daemon` — long-running process polling `djogi_live_plans` and resuming **only resume-safe steps** (`BackfillChunked`, `ValidateBackfill`) whose row is `running` with stale `last_progress_at`. Daemon mode never advances through `paused` rows (the operator's checkpoint state) and never crosses `CutoverReads` / `CutoverWrites` / `FinalizeConstraints` — those require explicit operator authorization. Daemon coordination uses Postgres advisory locks keyed on `SHA-256("djogi:live-plan:<plan-id>")` (first 8 bytes as big-endian `i64`, parallel to the migration advisory lock construction in the existing `Migration advisory lock key` row), held on a dedicated non-pooled `tokio_postgres::Client` for the full resume window — pooled connections cannot hold session advisory locks per the existing `Migration advisory lock connection` row. Multi-process / scheduler-driven coordination across machines is deferred to Phase 11 (Distributed Topology). **Lens:** scalability — long-running backfills survive operator crashes; production stability — daemon never advances cutover/finalize gates without operator action, and lock semantics match Phase 7's already-correct pattern; architectural — distributed coordination stays in its proper phase. |
| Custom-checks extensibility surface (Phase 7.5) | Adopters can register custom dangerous-op refusal rules via `djogi::live::register_check`. Signature: `fn(SchemaOperation) -> CheckResult` where `CheckResult::Refuse { reason: &'static str }` aborts the compose with the supplied reason. Registry is compile-time `inventory::collect!` (consistent with the apps + descriptor pattern); runtime registration is rejected. Per-org rules ship as crates that submit checks via `inventory::submit!`. **Lens:** scalability — large orgs can encode their own policies without forking; idiomatic Rust — same inventory pattern as descriptors / apps; simplicity — closed-form classifier for default users, extensible for those who need it. |

| Reserved identifier namespace (Phase 8-Zero) | The `__djogi_` prefix is reserved ASCII-case-insensitively for framework-internal SQL identifiers (recursive CTE names like `__djogi_tree` / `__djogi_closure`, derived-table aliases like `__djogi_q`, synthetic column aliases like `__djogi_agg_N` / `__djogi_edge_label` / `__djogi_search_seq` / `__djogi_parent_id`) and macro-emitted scratch identifiers in user crate scope (`__djogi_test_inner_<N>`, `__djogi_apps_invocation_sentinel`, etc.). | Djogi-as-dylib for shell + lihaaf (Phase 9) | 2026-05-10: djogi is buildable as a Rust dynamic library (`libdjogi.so`) and the Phase 9 shell binary dlopens it at startup; the lihaaf test harness shares the same coupling for its own reasons (see [`docs/spec/lihaaf-v0.1.md`](./lihaaf-v0.1.md), TBD). Rationale, in order of weight: (1) **Build iteration speed** — the shell crate (and lihaaf) iterates without re-linking djogi statically on every change, which collapses the inner loop for shell-side and harness-side work. (2) **Plugin ecosystem via `rhai-dylib`** — precompiled Rhai modules can ship as `.so` files that link against the canonical `libdjogi.so` rather than statically baking djogi into each plugin; as the module ecosystem grows this is the difference between linear and constant memory growth. (3) **Distribution size** — a ~5 MB shell binary plus a swappable ~30 MB `libdjogi.so` packages and ships better than a ~100 MB monolithic binary. (4) **Hot-reload potential** — speculative, not v0; rebuilding the dylib and dlopen-ing the new version into a running shell session is technically possible and the architecture leaves the door open. **Explicit non-goal:** dylib does NOT speed up runtime query execution. PLT/GOT indirection adds ~1-2 ns per cross-dylib call, lost in the noise next to the cheapest SQL round-trip. Anyone who frames dylib as a "faster queries" win is wrong; the speed wins are entirely on the build, plugin, memory, and distribution axes. **Spike-gated:** the inventory-on-dylib spike (see `docs/research/2026-05-10-inventory-on-dylib-spike.md`, TBD) validates whether `cargo rustc --crate-type=dylib` works for djogi AND whether `inventory::submit!` registrations propagate across the dylib boundary. Three contingencies named in `docs/spec/shell.md` §13.13 cover the fallback paths (`GO_WITH_MANIFEST` adds `crate-type = ["lib", "dylib"]` to djogi's `[lib]`; `GO_WITH_WORKAROUND` exposes explicit `lihaaf_inventory_collect_<T>()` per-collection re-exports; `NO_GO` ships Phase 9 statically-linked and defers the dylib-dependent benefits until the toolchain blocker resolves). The lihaaf harness consumes the same dylib but has no Rhai dependency — the dylib pattern is shared, the harnesses are independent. **Lens:** scalability — plugin ecosystem can grow without per-plugin memory cost; production stability — distribution surface stays bounded as djogi grows; honesty — the rationale names what dylib actually buys (build, plugin, memory, distribution) and explicitly disclaims the easy-but-wrong "faster execution" framing. |
