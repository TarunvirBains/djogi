# Topic 01: Source of Truth and State

## Executive summary

Every migration system surveyed answers two separable questions: (1) what schema is *desired*, and (2) what schema is *applied*. Where those answers live — and whether they are ever stored in the same artefact — is the deepest design split across the eleven systems.

The majority of systems store desired state in either ORM model code (Django, cot, SeaORM) or migration files themselves (Flyway, Liquibase, refinery, Diesel). A minority store desired state in a first-class descriptor artefact that is separate from both model code and migration files: Prisma uses a `.prisma` schema file; Djogi uses `target/djogi_models.json`. Alembic occupies a hybrid position — desired state lives in SQLAlchemy `MetaData` objects inside user application code, while migration files are the canonical execution artefacts. Diesel is similarly hybrid: `schema.rs` tracks the intended Rust-level schema, but migration SQL files are the execution authority, and the two can silently diverge.

The big finding is convergence on the ledger side: all eleven systems store applied-state in the database in a table keyed by migration identity, and all treat the filesystem (or compiled-in artefact) as the authority for *what to execute*. The divergence is entirely on the *desired-state* side. Djogi's choice — a build-time JSON descriptor as the sole source of desired state, with SQL migration files as the immutable execution record — is the same architectural bet as Prisma's, validated by five years of production use. The risk is that if `target/djogi_models.json` and the actual applied SQL diverge (e.g., a failed partial migration), there is no third source of truth to arbitrate. Djogi must plan a clear invariant: the JSON descriptor represents what `#[djogi::model]` structs describe *right now*; `schema_snapshot.json` represents what was last successfully migrated; the diff between them is what must be generated. When that invariant is violated, the runner must diagnose it explicitly rather than silently proceeding.

## Approaches

### Approach A: ORM-model-canonical

Systems: **Django**, **cot**, **SeaORM**

In this approach the Rust or Python ORM model definition is the single source of truth for *desired* state. The migration system exists to produce the SQL that closes the gap between what the ORM says and what the database has.

**Django** is the archetype. `models.py` files are the canonical schema description. The `MigrationAutodetector` (`django/db/migrations/autodetector.py:62-72`) diffs two `ProjectState` objects — one reconstructed from applied migration history, one built from the live model classes — and emits a list of `Operation` objects that bridges them. There is no persistent schema snapshot; `ProjectState` is always rebuilt by replaying every applied migration from scratch, an O(n) operation in migration count (`django/db/migrations/graph.py:315-332`). The in-memory `ProjectState` is the only record of desired-vs-applied gap; it is discarded at process exit. Confidence: **high**.

**cot** follows the same philosophy in Rust. `#[model]`-annotated structs in `src/**/*.rs` are the desired state. The CLI scans all Rust source files via `syn::parse_file` at invocation time and compares them against snapshot structs embedded inside previous migration files (`cot-cli/src/migration_generator.rs:198-213`). No database introspection, no JSON descriptor file — the migration files themselves carry a copy of each model at the time the migration was written. Confidence: **high**.

**SeaORM** is similar: the ordered `Vec<Box<dyn MigrationTrait>>` returned by `MigratorTrait::migrations()` is the authoritative ordered list of migrations (`sea-orm-migration/src/migrator.rs:56`). However SeaORM does not provide autogeneration from model definitions — users write migration code by hand. The "canonical source" is therefore the Rust migration code, not the entity structs. Confidence: **high**.

**Shared properties and risks:** All three rebuild desired state at runtime from live code. There is no persistent, versionable desired-state artefact that can be reviewed in a PR before the migrations are generated. In Django's case this has a known cost: O(n) replay grows with project age (`django.md` Surprise 5). In cot's case, the snapshot-in-migration-file design couples the operational plan to the snapshot, so hand-editing operations without updating the snapshot generates incorrect future diffs (`cot.md` Surprise 3). SeaORM avoids the coupling by not having autogeneration at all, shifting the full burden to the developer.

None of the three systems store a checksum of the desired-state representation in the ledger. Django and cot have no checksum at all (`django/db/migrations/recorder.py` — no hash field; `cot.md` confirmed by grep). SeaORM's `seaql_migrations` table has two columns: `version` and `applied_at` (`sea-orm-migration/src/seaql_migrations.rs:1-15`). Any of the three will silently accept a post-apply mutation of the migration definition.

### Approach B: Migration-file-canonical

Systems: **Flyway**, **Liquibase**, **refinery**, (and partially **Diesel**)

In these systems, migration files (SQL scripts or changelog XML/YAML) are both the desired-state description and the execution artefact. There is no ORM model layer that independently describes the schema; the schema is whatever the migrations, applied in order, produce.

**Flyway** is the cleanest example. A `V2__add_column.sql` file is the migration, full stop. The `flyway_schema_history` table records what has been applied, with CRC-32 checksums computed from file content (`flyway-core/src/main/java/org/flywaydb/core/internal/resolver/ChecksumCalculator.java:41-87`). Drift detection compares the on-disk checksum against the stored checksum at every `migrate` invocation via `MigrationInfoServiceImpl.refresh()` (`flyway-core/src/main/java/org/flywaydb/core/internal/info/MigrationInfoServiceImpl.java:91`). There is no separate model layer; Flyway never generates migrations — users write them. Confidence: **high**.

**Liquibase** uses a structured changelog (XML, YAML, JSON, or SQL) that is both migration definition and identity source. The `(ID, AUTHOR, FILENAME)` triple — not the file content — is the changeset identity (`liquibase-standard/src/main/java/liquibase/changelog/ChangeSet.java:117-129`). Checksums cover the *parsed Change DSL*, not the emitted SQL (`liquibase-standard/src/main/java/liquibase/changelog/ChangeSet.java:396-422`), which means a Liquibase version upgrade that changes SQL generation does not trigger a checksum mismatch. Confidence: **high**.

**refinery** stores SQL files (or compiles them in via `embed_migrations!`). Its SipHash-1-3 checksum covers name + version + SQL content (`refinery_core/src/runner.rs:92-96`). Unlike Flyway, which checksums file content alone, refinery includes `name` and `version` in the hash, meaning a file rename changes the checksum even if SQL is unchanged. Applied state is tracked in `refinery_schema_history` with `version` as the integer primary key. Confidence: **high**.

**Diesel** sits at the boundary between approaches B and D. SQL files are the execution artefacts, but `schema.rs` (generated by `diesel print-schema`) is a secondary desired-state representation that the `--diff-schema` autogen tool reads. However `schema.rs` is not authoritative: it is re-derived from the live database after each migration run (`diesel_cli/src/migrations/mod.rs:208`), and the `--diff-schema` tool is explicitly labeled not production-ready (`diesel_cli/src/migrations/mod.rs:127-131`). In practice Diesel users write all migrations by hand, making it effectively migration-file-canonical. No checksum on migration files (`diesel.md` confirmed by grep). Confidence: **high**.

**Shared properties and risks:** Migration-file-canonical systems offload the "generate migration" problem entirely to the user or to a separate tooling layer. They are simple to understand: the ledger tells you what ran; the files tell you what to run next. The risk is that the actual live database schema can drift from what the migration history implies, with no way to detect it without replaying the entire history against a shadow database (which Prisma does, but none of the systems in this group do).

### Approach C: Descriptor-file-canonical

Systems: **Prisma**, **Djogi** (planned)

In this approach a dedicated artefact — separate from both application code and migration files — is the source of truth for desired schema. This artefact is declarative, versionable, and human-readable.

**Prisma** uses `schema.prisma` (PSL — Prisma Schema Language). Every downstream artefact is derived from it: migration SQL files are generated by diffing the PSL against a shadow database (which has had all prior migrations applied) (`packages/migrate/src/SchemaEngine.ts:21-23`). The PSL file is tracked in version control. When the database drifts from what the migration history implies, `prisma migrate dev` detects it via the shadow-DB diff and reports `driftDetected` (`packages/migrate/src/types.ts:54-61`). The `_prisma_migrations` ledger stores `applied_steps_count` per migration, enabling mid-migration failure tracking (`packages/migrate/src/SchemaEngine.ts:91-95`). The `migration_lock.toml` file pins the database provider, preventing cross-provider history corruption (`packages/migrate/src/utils/createMigration.ts:47-53`). Confidence on architecture: **high**; on ledger DDL specifics: **medium-low** (Rust engine not in this clone).

**Djogi** uses `target/djogi_models.json` generated at build time from `#[djogi::model]` Rust structs via `build.rs`. The JSON descriptor is the desired state; `schema_snapshot.json` is the last-migrated state; `build.rs` diffs these to produce paired `NNNN_name_up.sql`/`NNNN_name_down.sql` files. The SQL files are then immutable history. This is structurally identical to Prisma's approach with two differences: (1) Djogi's descriptor is produced by a Rust build step rather than hand-authored PSL; (2) the shadow-DB comparison Prisma uses to detect drift is replaced by a JSON diff, which is cheaper but less able to detect external mutations (e.g., an ops engineer adding a column directly).

**Shared properties:** Descriptor-canonical systems make the desired schema reviewable independently of migration history. A PR that changes `schema.prisma` or a `#[djogi::model]` struct shows exactly what schema change is being proposed, before the migration is generated. Migration files, once written, are intended to be immutable history — they should not need to be re-read to understand desired state.

The critical weakness of both is that the descriptor and the migration history can silently diverge if a migration is manually edited after generation, or if a non-Prisma/non-Djogi tool modifies the database schema. Prisma addresses this with shadow-DB replay; Djogi's current spec relies on checksums in the ledger but does not describe a shadow-DB mechanism. This is an open design gap (see Open questions).

### Approach D: Hybrid

Systems: **Alembic**, **SQLAlchemy** (schema layer), **Diesel**

In hybrid systems, desired state is expressed in application code (SQLAlchemy `MetaData`, Diesel `schema.rs`) but execution state is in migration files. The application code and the migration files are maintained separately and can drift without automated enforcement.

**Alembic** with SQLAlchemy is the most mature hybrid. The `env.py` file wires the user's `MetaData` to Alembic's autogenerate pipeline. `AutogenContext` holds both the `MetaData` (desired) and a live database connection (actual), and the `_autogen_for_tables` pipeline diffs them (`alembic/autogenerate/compare/tables.py:36-83`). The result is a migration script written to `versions/`. After this point, the migration script is the canonical execution artefact, and `alembic_version` tracks which scripts have run. Crucially, there is no checkpoint between "model changed" and "migration written": if a developer changes the `MetaData` without running `alembic revision --autogenerate`, the change is invisible to the migration system until a human runs that command. The `alembic check` command (`command.py:323-378`) provides a CI gate that raises `AutogenerateDiffsDetected` if there are unapplied model changes. Confidence: **high**.

**Alembic's version table** (`alembic_version`) stores only the active head revision(s) — not a log of every migration (`alembic/ddl/impl.py:151-183`). When there are multiple unmerged branches, there is one row per active head. There is no `applied_at` timestamp, no checksum, no execution time. The table is purely a set of current position indicators. Confidence: **high**.

**Diesel's** `schema.rs` is explicitly not an authoritative desired-state representation — it is a *reflection* of the live database, regenerated by `diesel print-schema` after migrations run. The `--diff-schema` autogen tool reads `schema.rs` to compute a diff, but the tool itself is labeled experimental and does not handle composite FKs (`diesel_cli/src/migrations/diff_schema.rs:146-150`). Diesel is better classified as migration-file-canonical with an optional schema-reflection layer. Confidence: **high**.

## Convergence

All eleven systems agree on three invariants:

1. **Applied state lives in the database.** Every system that has a runner maintains at least one table in the database recording which migrations have been applied. The minimum viable ledger — seen in SeaORM (`seaql_migrations`) and cot (`cot__migrations`) — is two columns: migration identity and timestamp. Alembic's table is even more minimal: one column, `version_num`, with a primary key.

2. **The filesystem (or compiled-in binary) is the authority for what to execute.** No system reads migration SQL from the database. The database ledger says *what ran*; the filesystem says *what to run*. This separation is universal.

3. **Applied migrations are identified by a string key.** Django uses `(app, name)`; Flyway uses `installed_rank` + `version`; Liquibase uses `(ID, AUTHOR, FILENAME)`; refinery uses an integer `version`; Alembic uses `version_num` (12-char hex); Prisma uses `migration_name`; Diesel/SeaORM/cot use a version string from the filename. All identify migrations by something derivable from the filename or migration definition — none use opaque database-generated IDs as the primary cross-system identity.

## Divergence

The systems split on four dimensions:

**1. Where desired state lives and who writes it.**

ORM-model-canonical systems (Django, cot) require developers to keep ORM model definitions up-to-date and then generate migrations as a derived artefact. If a developer forgets to run `makemigrations` / `cot migration make`, the divergence is invisible until CI or a runtime check catches it.

Migration-file-canonical systems (Flyway, Liquibase, refinery) require developers to write migration SQL by hand. There is no automated desired-state model; "what the database should look like" is the union of all applied migrations.

Descriptor-canonical systems (Prisma, Djogi) require developers to maintain a separate artefact (`schema.prisma`, `#[djogi::model]` structs) from which migrations are auto-generated. The descriptor is the single source of truth; migration files are immutable, derived history.

**2. Checksum coverage and checksum-free systems.**

Flyway (CRC-32, `flyway-core/src/main/java/org/flywaydb/core/internal/resolver/ChecksumCalculator.java:41-87`), Liquibase (MD5 with version prefix, `liquibase-standard/src/main/java/liquibase/change/CheckSum.java:85-91`), refinery (SipHash-1-3, `refinery_core/src/runner.rs:92-96`), and Prisma (unknown algorithm in Rust engine) all store checksums in the ledger and validate them on each run. Django, Alembic, Diesel, SeaORM, and cot store no checksum and cannot detect post-apply mutation of migration files. Djogi plans checksums.

**3. Separation of applied-state ledger from execution history.**

Most systems conflate them in one table. Liquibase's `DATABASECHANGELOG` is closest to having both: the same row is updated on re-run (`EXECTYPE='RERAN'`, `MarkChangeSetRanGenerator.java:65-84`), which overwrites history. Prisma is the only system that explicitly tracks partial-apply state (`applied_steps_count`, `rolled_back_at`), keeping failed migration rows as audit trail rather than deleting them (`packages/migrate/src/SchemaEngine.ts:99-102`). Flyway records `success=false` rows for failed non-transactional migrations (`DbMigrate.java:257-261`), but removes them on `repair`. All other systems have binary applied/not-applied state.

**4. Which artefact wins when desired state and applied state diverge.**

For ORM-model-canonical systems, the ORM model wins by definition: developers are expected to generate a new migration for every model change. For migration-file-canonical systems, the filesystem wins: what's on disk is what should be applied. For descriptor-canonical systems like Prisma, the descriptor wins — and drift (database != what history implies) is an error condition. Djogi intends the descriptor to win, but the mechanism for detecting descriptor-vs-snapshot-vs-applied divergence at runtime is underspecified in the current spec.

## Djogi implications

**Adopt: Descriptor-canonical architecture is validated.**

Prisma's five-year track record confirms that a dedicated descriptor file as the single source of desired state is practical at scale (`prisma.md`, state model section, confidence: high). Djogi's `target/djogi_models.json` is the correct artefact to play this role. The Prisma parallel is direct: PSL file → Rust engine diff → `migration.sql`. Djogi: `#[djogi::model]` structs → `build.rs` → `djogi_models.json` diff → `NNNN_name_up.sql`.

**Adopt: `schema_snapshot.json` breaks Django's O(n) replay problem.**

Django rebuilds `ProjectState` from scratch by replaying every applied migration on every run (`django/db/migrations/graph.py:315-332`). This is O(n) in migration count and a known pain point for large projects (`django.md` Surprise 5). Djogi's `schema_snapshot.json` — representing the last-successfully-migrated state — breaks this dependence entirely. The differ operates against the snapshot, not against a replay. This is a genuine architectural improvement over the ORM-model-canonical approach.

**Adopt: Checksum in the ledger, with format versioning.**

Flyway (CRC-32), Liquibase (`V:hex` MD5), and refinery (SipHash-1-3 decimal) all prove that checksums in the ledger are operationally necessary. Django, Alembic, Diesel, SeaORM, and cot all lack checksums, making post-apply mutation silent. Djogi must include checksums. The format should include a version prefix (`V1:...`) following Liquibase's pattern (`liquibase-standard/src/main/java/liquibase/change/CheckSum.java:124-126`) so the algorithm can be upgraded without breaking existing ledgers. The algorithm should be SHA-256 (not CRC-32 per `flyway.md` reject), hashing only the SQL content with line-endings normalized to `\n` (per refinery's warning at `refinery.md` Surprise — no line-ending normalization). Do not hash name or version into the checksum (contra refinery's `runner.rs:92-96`), as this would break checksum continuity on file renames.

**Adopt: `applied_steps_count` and failed-migration retention.**

Prisma is the only system that keeps failed migration rows in the ledger as audit trail (`packages/migrate/src/SchemaEngine.ts:99-102`) and tracks how many DDL statements within a migration succeeded before failure (`applied_steps_count`). All other systems have binary applied/not-applied state, which is operationally insufficient for non-transactional migrations. Djogi's planned richer ledger (execution mode, partial-apply marker) aligns with Prisma's approach and should explicitly retain failed rows.

**Adopt: Three history-diagnostic states from Prisma.**

Prisma's `HistoryDiagnostic` discriminated union (`packages/migrate/src/types.ts:63-74`) — `databaseIsBehind`, `migrationsDirectoryIsBehind`, `historiesDiverge` (with `lastCommonMigrationName`) — is the minimal information-preserving taxonomy for describing migration state mismatches. Djogi's `migrate status` command should produce equivalent structured output rather than a generic error message.

**Reject: ORM-model-canonical for the differ.**

Django's approach of diffing live ORM classes against a replayed `ProjectState` (django/db/migrations/autodetector.py) requires that desired state be expressed as live Python classes. Djogi's Rust structs cannot play this role at runtime — the differ must operate against a serialized artefact (`djogi_models.json`). cot's approach of scanning Rust source with `syn::parse_file` at CLI time is the closest Rust equivalent to Django's approach, but it has the coupling problem noted above and lacks support for types beyond the cross-DB `ColumnType` enum (`cot.md` schema metadata section). Djogi's build-time JSON descriptor is strictly better than either.

**Reject: Alembic's version-table-only ledger.**

Alembic's `alembic_version` table stores only `version_num` — no timestamp, no checksum, no execution duration (`alembic/ddl/impl.py:151-183`). This is the minimum viable ledger and provides no operational value beyond "is this applied." Djogi's planned richer ledger is justified by every system that has actually been used in production at scale (Flyway's `installed_on`, `execution_time`, `success`; Liquibase's `DATEEXECUTED`, `ORDEREXECUTED`, `DEPLOYMENT_ID`; Prisma's `started_at`, `finished_at`, `rolled_back_at`, `applied_steps_count`).

**Defer: Shadow-DB drift detection.**

Prisma's most powerful drift detection mechanism is shadow-DB replay: apply all migrations to a disposable DB, then diff against the real DB (`packages/cli/src/mcp/MCP.ts:85`). This detects schema drift introduced by out-of-band DDL (e.g., an ops engineer ran `ALTER TABLE` directly). Djogi has no equivalent mechanism. The descriptor-based approach can only detect drift between the descriptor and the snapshot, not between the snapshot and the actual database. A `djogi migrate check --live` mode that introspects the live database against `schema_snapshot.json` would close this gap but is out of scope for 0.1.0.

**Open design gap: snapshot invariant on partial migration failure.**

The current spec states that `schema_snapshot.json` is updated only on successful `cargo djogi migrate`. If a migration fails after some DDL has executed (non-transactional migration), the snapshot will be behind the descriptor but also behind the actual database state. There is no third source to arbitrate. Djogi needs an explicit invariant: on any migration failure, the runner must write a `migration_failure.json` or equivalent marker so the next invocation knows it is starting from a potentially inconsistent state rather than a clean "snapshot is authoritative" state.

## Open questions

1. **Snapshot vs. live-DB authority.** When `schema_snapshot.json`, `djogi_models.json`, and the actual database all disagree, which wins? The spec implies `djogi_models.json` always wins, but this is only safe if the ledger checksum confirms the applied SQL has not been externally mutated. Document this invariant explicitly, with the failure mode for each of the three possible discrepancies.

2. **Shadow-DB or inspector-based drift detection.** Prisma uses a shadow DB; Alembic uses live introspection through the SQLAlchemy `Inspector`. Djogi currently has neither. For `0.2.0`, should `migrate check --live` introspect `pg_catalog` and compare against `schema_snapshot.json`? The SQLAlchemy `pg_catalog` query patterns (`sqlalchemy.md`, reflection section) are the reference implementation for Postgres-specific introspection.

3. **Snapshot update timing on non-transactional migrations.** For migrations with `execution_mode = no_txn`, the DDL commits per-statement without a wrapping transaction. At what point is `schema_snapshot.json` updated? If it is updated atomically with the ledger INSERT, and the ledger INSERT is outside the DDL transaction, there is still a gap. This needs a precise commit sequence documented in the runner spec.

4. **Model-removed but migration not written.** If a developer removes a `#[djogi::model]` struct, `build.rs` will generate a migration with a `DROP TABLE`. But if the developer never runs `cargo djogi migrate` before the next deploy, the table persists in the database while the descriptor says it should not exist. Django's `makemigrations --check` provides a CI gate for this pattern (`django/core/management/commands/migrate.py`); Alembic's `alembic check` is equivalent (`command.py:323-378`). Djogi needs a `cargo djogi migrate check` (or build-time warning escalated to error in CI) that exits non-zero if the descriptor has drifted from the snapshot.

5. **Applied migration removed from descriptor (Liquibase's `MISSING_SUCCESS` state).** If a migration SQL file is deleted from the filesystem after being applied — developer accidentally removes it, or intentional squash — every system handles this differently: refinery errors by default (`abort_missing = true`); SeaORM errors (`exec.rs:59-66`); Flyway enters `MISSING_SUCCESS` state and proceeds unless strict mode is on. Djogi's policy on this case is unspecified in the current spec.
